# 아파트 감별사 레드팀

## 왜 이 스킬이 있나

이 서비스는 로그인·집계·운영자 전용 화면·사용자가 써 넣는 글을 전부 직접 구현했다.
의존성을 늘리지 않으려고 그렇게 했고, 그 대가로 **남이 대신 검증해 주는 부분이 없다.**
그래서 공격자 입장에서 한 번씩 찔러 보는 자리를 따로 둔다.

**QA 스킬과 다른 점**: QA는 "쓰기 불편한가"를 본다. 여기는 "못 하게 막아 둔 것을
할 수 있는가"를 본다. 통과 기준도 다르다 — QA는 화면이 예뻐야 통과지만, 여기는
**막혔다는 증거**가 있어야 통과다.

**가장 중요한 규칙: 실제로 해 본다.**
"코드에 가드가 있다"는 통과가 아니다. 쿠키를 위조해서 던져 보고, 정답을 캐내 보고,
비밀을 찾아본 것만 통과다. 못 뚫은 것은 못 뚫었다고 쓰고, 뚫린 것은 **어떻게 뚫었는지
재현 순서와 함께** 쓴다.

## 실행

```bash
cd web && npm run build && DATABASE_URL= npm start &   # 반드시 DB를 떼고 띄운다
node .claude/skills/redteam/scripts/redteam.mjs [all|session|guard|answer|input|secret|header]

# 계정 쪽 잠금만 따로 (DB를 붙여 띄운 뒤)
REDTEAM_DB=1 node .claude/skills/redteam/scripts/redteam.mjs answer
```

**`DATABASE_URL=`을 비우는 이유**: 이 점검은 일부러 쓰레기 값을 밀어 넣는다.
운영 연결 문자열이 붙어 있으면 그 쓰레기가 운영 집계에 그대로 들어간다.

**운영 사이트(apt-game.app)에 대고 돌리지 않는다.** 로컬에서만 돌린다.
남의 서비스에 같은 짓을 하면 공격이다. 여기서 허용되는 건 자기 것을 자기가 두드리는 것뿐이다.

세션 위조 검사는 `web/.env.local`의 `AUTH_SECRET`으로 정상 토큰을 하나 만들어
대조군으로 쓴다. **키를 알아야만 통과하는 것**이 곧 통과 조건이라서다.
키가 없으면 그 항목은 "확인 못 함"으로 남긴다 — 조용히 통과시키지 않는다.

## 점검 항목과 그 항목이 생긴 이유

### 1. 세션 (`session`)
HMAC 서명 쿠키 하나가 로그인·운영자 권한을 전부 짊어진다. 여기가 뚫리면 나머지는 의미가 없다.

| 찔러 보는 것 | 통과 기준 |
|---|---|
| 쿠키 없이 내 기록 요청 | 401 |
| 서명을 뗀 토큰 | 401 |
| 본문만 바꾸고 옛 서명을 붙인 토큰 | 401 |
| 서명은 맞지만 만료된 토큰 | 401 |
| `own: true`를 스스로 적어 넣은 토큰 | 운영자 화면 404 |
| 서명 자리에 빈 문자열·길이가 다른 값 | 401 (`timingSafeEqual`이 길이 차이에 던지지 않는가) |
| 키로 제대로 서명한 토큰 (대조군) | 200 — 키를 알아야만 된다는 증거 |

### 2. 창구 가드 (`guard`)
전개 전 창구와 운영자 화면은 **숨기는 것과 막는 것이 다르다.** 홈에서 안 보이게만
하면 주소를 아는 사람은 그냥 들어온다. 화면(`requireReleased`)과 데이터
(`blockIfUnreleased`) 양쪽이 같이 막혀 있어야 한다.

- 비로그인·일반 로그인 둘 다로 전개 전 창구의 **화면과 API를 모두** 찔러 본다.
- 운영자 전용(`/ops`, `/report`, `/api/ops`, `/api/report`, `/api/coined`, `/api/bug` 목록)도 같이.
- **404여야 한다.** "권한이 없습니다"라고 답하면 안 연 창구가 있다는 사실 자체를
  알려 주는 셈이다. 응답 본문에 unauthorized·forbidden 같은 말이 있으면 실패다.
- 운영자로는 열리는지도 확인한다. 전부 404면 가드가 아니라 그냥 고장 난 것이다.

### 3. 정답 유출 (`answer`)
"정답은 클라이언트에 내려주지 않는다"가 이 서비스의 뼈대다. 내려가는 순간 게임이 끝난다.

| 찔러 보는 것 | 통과 기준 |
|---|---|
| 각 창구의 출제 응답 | `kind`·`real`·`fake`·`answer` 같은 키가 없다 |
| 첫 HTML과 클라이언트 번들 | 가짜 이름 목록·정답 배열이 실려 있지 않다 |
| 집계를 건너뛰는 스위치가 남아 있는가 | 흔적 없이 정답표를 만들 수 있는가 |
| 한 판에서 답을 바꿔 보기 | 두 번째 답이 첫 판정 그대로인가 |
| 판 쿠키를 버리고 다시 답해 보기 | 계정에 첫 답이 남아 판정이 안 바뀌는가 |

**즉시 정답 공개는 설계다.** 첫 답에 정답이 드러나는 것은 못 막는다 — 막아야
하는 건 알고 나서 답을 바꾸는 쪽이다. 그래서 통과 기준이 거절(409)이 아니라
**첫 답 고정**이다. 네트워크가 끊겨 같은 요청이 두 번 가는 일이 실제로 있고,
그때 막아 버리면 정직하게 친 사람이 문제를 잃는다.

계정 쪽 잠금은 DB가 있어야 잰다. 이 점검은 DB를 떼고 돌리는 것이 규칙이라,
그 항목만 따로 확인한다 — DB를 붙여 띄운 뒤 `REDTEAM_DB=1`을 준다.
`.env.local`에 연결 문자열이 있는 것과 지금 띄운 서버가 DB에 붙어 있는 것은
다르다. 파일만 보고 판단했다가 방어가 뚫렸다고 잘못 적은 적이 있다.

비회원이 쿠키를 버리고 판을 새로 열면 한 문제씩은 여전히 캘 수 있다. 판을
계정에 묶기 전까지 남는 구멍이고, 못 막는 것을 막았다고 적지 않는다.

### 4. 입력 검증 (`input`)
사람이 써 넣는 자리가 넷이다: 작명 이름, 버그 제보 본문, 기록 동기화 본문, 구역 값.

- 아주 긴 문자열, 제어문자, HTML 태그, SQL 조각, 유니코드 방향 제어문자를 넣는다.
- 통과 기준은 **거부하거나 안전하게 저장하되 500이 나지 않는 것**이다.
  500은 예상 못 한 입력이 안쪽까지 들어갔다는 뜻이다.
- 구역 값은 모르는 값이면 전국으로 떨어져야 한다. 임의 문자열이 집계 테이블에
  쓰레기 구역을 만들면 순위가 통째로 흔들린다.
- 기록 동기화는 본문 크기 상한과 구역 수 상한이 실제로 걸리는지 본다.
- 버그 제보는 본인 확인 없이 들어가는지, 허니팟 칸이 조용히 먹는지 본다.

### 5. 비밀 유출 (`secret`)
커밋 메시지가 공개 블로그로 그대로 나가는 레포다. 한 번 새면 되돌릴 수 없다.

- 추적되는 파일과 최근 커밋 메시지에서 연결 문자열·인증키·서명 키 패턴을 찾는다.
- `.env.local`이 무시 목록에 있고 추적되지 않는지 확인한다.
- **빌드된 클라이언트 번들에 실제 환경변수 값이 섞였는지** 그 값으로 직접 찾는다.
  (`NEXT_PUBLIC_` 접두사 없이도 실수로 클라이언트 컴포넌트에서 읽으면 들어간다.)
- 소스맵이 함께 배포되는지 본다.

### 6. 헤더·리디렉션 (`header`)
- 세션 쿠키가 HttpOnly·SameSite인가. 아니면 스크립트가 읽어 간다.
- 개인 기록 응답에 `Cache-Control: no-store`가 붙는가. 캐시에 남으면 남이 본다.
- 로그인 시작이 `redirect_uri`를 요청 값으로 만들지 않는가(오픈 리디렉트).
- 쿼리로 임의 주소를 넘겨 로그인 뒤 그리로 보내지는가.

## 보고 방식

- 통과는 한 줄. **실패는 재현 순서·요청·응답을 그대로** 쓴다.
- 자동으로 못 보는 것은 "확인 못 함"으로 남긴다. 통과로 묶지 않는다.
- 뚫린 것이 나오면 고치기 전에 **무엇을 할 수 있게 되는지**를 먼저 쓴다.
  영향이 없으면 고칠 순서가 뒤로 가도 된다.

## 사람이 봐야 하는 것 (자동화 못 함)

- 구글 콘솔의 리디렉션 URI 목록이 실제로 하나인가
- Vercel 환경변수가 Secret으로 들어가 있는가, 미리보기 배포에도 같은 값이 붙는가
- 운영자 계정(`OWNER_EMAIL`)의 구글 계정 자체가 2단계 인증을 쓰는가
- DB 접속이 신뢰하는 곳에서만 열려 있는가
